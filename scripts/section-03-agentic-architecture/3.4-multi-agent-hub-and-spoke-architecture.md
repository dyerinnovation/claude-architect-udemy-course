Single agents are powerful. But they have limits. One context window. One thing at a time. Complex tasks — research pipelines, code review, customer support — often need multiple specialized capabilities running in parallel. Multi-agent systems solve that — but they introduce coordination challenges. The architecture the CCA-F exam tests is hub-and-spoke: a central coordinator managing multiple specialized subagents. ## SLIDE 4: Hub-and-Spoke — The Core Structure

**Visual**: Hub-and-spoke diagram. Center hub: "Coordinator Agent" (large, blue). Four spokes extending to smaller nodes: "Research Subagent", "Document Analysis Subagent", "Synthesis Subagent", "Report Generation Subagent". No arrows between the outer nodes — only between each node and the hub. Label: "Subagents never communicate directly with each other."

Let's start with the core topology — the defining shape of hub-and-spoke.

The hub-and-spoke pattern has one defining rule: **all communication flows through the coordinator**.

The coordinator — the hub — receives the original task. It decomposes it. It assigns work to subagents. It collects results. It aggregates. And it produces the final output.

[click]

The subagents — the spokes — only ever communicate with the coordinator. They never talk directly to each other.

This is not a limitation. It's a deliberate design choice that gives you centralized observability, consistent error handling, and predictable control flow. If subagents communicated directly, you'd have a mesh topology — harder to debug, harder to monitor, and harder to reason about when something goes wrong. With the topology set, let's look at what the coordinator actually does.

---

## SLIDE 5: The Coordinator's Three Jobs

**Visual**: Three-step process diagram with icons. Step 1: "Decompose" (puzzle piece icon). Step 2: "Delegate" (arrow pointing outward icon). Step 3: "Aggregate" (merge arrows icon). Each step has 2-3 bullet points of detail. Light background.

Now let's name what the coordinator is actually doing.

The coordinator has exactly three jobs: decompose, delegate, and aggregate.

**Decompose**: break the original task into pieces that subagents can handle independently. Good decomposition means each subagent has a clear, bounded responsibility with no implicit dependencies on what other subagents are doing.

[click]

**Delegate**: spawn each subagent with its specific task and the context it needs. This means explicit context passing — subagents don't inherit the coordinator's history. Each one starts fresh.

[click]

**Aggregate**: collect all the subagent outputs, synthesize them into a coherent response, and handle any failures gracefully. The coordinator is responsible for catching subagent errors and deciding whether to retry, skip, or surface the failure. Next, let's zero in on that fresh-context rule — it's the part candidates get wrong most often.

## SLIDE 6: Subagent Context Isolation

**Visual**: Side-by-side comparison. Left: "What candidates assume" — coordinator with full history, arrow to subagent with "inherits history". Right: "What actually happens" — coordinator has history, arrow to subagent with "starts fresh, gets only what coordinator passes". Red X on left, green check on right.

Now let's go deeper on the fresh-context rule — the part candidates get wrong most often.

One of the most important things to understand about subagents: they don't inherit the coordinator's conversation history. Each subagent starts with a completely fresh context.

[click]

This means the coordinator must be explicit about what information each subagent needs. If the research pipeline has already found key facts, and the synthesis subagent needs those facts, the coordinator must explicitly include them in the synthesis subagent's task prompt.

Nothing flows implicitly. Everything that matters must be passed explicitly. This is why the exam asks about "explicit context passing" — it's the mechanism that makes multi-agent systems actually work. With the fresh-context rule in mind, let's look at the actual tool that spawns subagents.

## SLIDE 7: The Task Tool — Spawning Subagents

**Visual**: Code-style diagram showing a coordinator spawning a subagent using the Task tool. Shows the Task call with task, instructions, and allowedTools parameters. Highlight box on `allowedTools` with note: "Must include 'Task' for the subagent to accept its assignment."

Here's the actual mechanism — the Task tool.

In Claude's agent framework, coordinators spawn subagents using the `Task` tool. A Task call has three key parameters: the task description (what to do), the instructions (context and constraints), and `allowedTools` (what tools the subagent is permitted to use).

[click]

The `allowedTools` parameter is an exam favorite. For a subagent to receive and process its task, `allowedTools` must include `"Task"`. Without it, the subagent can't properly accept the task specification.

Think of it this way: the Task tool is how an agent formally accepts an assignment. No Task in `allowedTools` means no assignment accepted. With Task understood, let's look at how the coordinator runs subagents — one at a time, or all at once.

## SLIDE 8: Parallel vs Sequential Subagent Execution

**Visual**: Two workflow diagrams stacked vertically. Top: "Sequential execution" — subagent 1 → wait → subagent 2 → wait → subagent 3. Amber clock icon. Bottom: "Parallel execution" — all three subagents spawned simultaneously from coordinator, arrows all pointing back to coordinator at same time. Green speed icon.

Now let's look at parallel versus sequential execution.

The hub-and-spoke architecture supports both. Sequential: the coordinator spawns one subagent, waits for the result, then spawns the next. Use this when subagent B depends on subagent A's output.

[click]

Parallel: the coordinator spawns multiple subagents in a **single response turn**. This is the key phrase for the exam. All parallel subagent spawning happens in one coordinator turn — multiple Task calls in one response. The coordinator then waits for all results before continuing.

Parallel execution is the right choice when tasks are independent. The multi-agent research pipeline spawns document analysis, web search, and source verification subagents in parallel because their work doesn't depend on each other. With that distinction made, here's the exam tip the entire lecture builds toward.

## SLIDE 9: Exam Tip

**Visual**: Amber callout box. Title: "Exam Tip". Two bullets: "Parallel subagents: ALL spawned in ONE coordinator response turn." and "Subagents never communicate directly — all traffic flows through the coordinator."

Here's the exam tip that distills the lecture.

Two patterns the exam tests heavily in the hub-and-spoke context.

First: parallel subagent spawning happens in **one** coordinator response. The exam will offer an answer where the coordinator spawns subagents sequentially across multiple turns. That's slower and misses the point of parallelism. Classic almost-right distractor — sequential spawning looks like it still produces the same result, but it's the wrong pattern.

Second: direct subagent-to-subagent communication is **always wrong** in this architecture. If an answer choice has subagents sharing information directly, it's violating hub-and-spoke. In hub-and-spoke, everything goes through the coordinator. Last up: the takeaways to lock in.

## SLIDE 10: Key Takeaways

**Visual**: Clean bullet list on light background. Title: "Hub-and-Spoke Architecture".

Here are the six takeaways to carry forward.

- **All communication flows through the coordinator** — subagents never talk directly to each other
- The coordinator's three jobs: **Decompose → Delegate → Aggregate**
- Subagents have **no inherited context** — coordinator must pass everything explicitly
- `allowedTools` must include `"Task"` for a subagent to accept its assignment
- **Parallel spawning = all subagents spawned in one coordinator response turn**
- Hub-and-spoke is used in Scenarios 1 (Customer Support) and 3 (Research System)
