## SLIDE 4: The tool_use Path — Step by Step

**Visual**: Four sequential numbered steps. Step 1: "Receive response with stop_reason = tool_use". Step 2: "Extract tool_use blocks from content array". Step 3: "Execute each tool". Step 4: "Append assistant msg + tool results, send next request". Each step in a card, connected by arrows.

Let's walk the `tool_use` path one step at a time.

When you receive a response with `stop_reason = "tool_use"`, here's the exact sequence. Step one: extract the tool_use blocks from the content array. A single response can contain multiple tool_use blocks — Claude can call several tools in one turn.

[click]

Step two: execute each tool. This means running your actual function — querying a database, calling an API, reading a file — whatever the tool does.

[click]

Step three: package the results. Each result goes into a `tool_result` block with the matching `tool_use_id`, the content — the actual result data — and an `is_error` flag if the tool failed.

[click]

Step four: append the original assistant response to messages, then append a new user message containing all the tool results. Then call the API again. With the `tool_use` path nailed down, let's flip to what `end_turn` actually means.

## SLIDE 5: The end_turn Path — What It Actually Means

**Visual**: Decision tree. `stop_reason = "end_turn"` at top. Three branches below: "Successful completion", "Blocked / can't proceed", "Max tokens reached". Each branch has a description and "What to do" note. Amber box for max_tokens case.

Now let's look at the `end_turn` path — and why it doesn't always mean "everything's fine."

`"end_turn"` means Claude has decided to stop generating — for whatever reason.

[click]

The three typical reasons are: the task is complete (the most common case), Claude determined it cannot proceed and is returning an explanation, or the context got close to the limit. In your control flow, you should inspect the response content after an `"end_turn"` to understand *why* Claude stopped — especially in error-prone workflows.

But critically: do not loop on `"end_turn"`. Whatever the reason, Claude has made a decision. Return the response and let the calling code or user handle it. Next, the bigger architectural choice — who decides which tool to call.

## SLIDE 6: Model-Driven vs Pre-Configured Decision Trees

**Visual**: Two-column comparison. Left: "Model-Driven (Claude decides)". Right: "Pre-Configured (your code decides)". Example in each column. Light background.

Now let's zoom out to the bigger architectural choice: who decides which tool gets called.

In the **model-driven** approach, you give Claude a full set of tools and let it decide which to call and in what order. The tool_use loop handles sequencing automatically. Claude's judgment is the routing logic.

[click]

In the **pre-configured** approach, your code has explicit decision trees. Certain tools can only be called after others complete. You inspect intermediate results and decide what to do next.

For exam purposes: model-driven is the default for flexible workflows. Pre-configured — what we'll later call programmatic enforcement — is the right choice for **hard constraints** — things that must happen in a specific order for safety or correctness reasons.

Scenario 1, customer support, uses this explicitly: you can't process a refund before looking up the customer order. That order enforcement is programmatic, not left to Claude's judgment. This is one of the six scenarios from 1.1 — and remember, you don't pick the four that appear on your exam, so you prepare for this one either way. ## SLIDE 7: Handling Multiple Tool Calls in One Response

**Visual**: Code block showing a response with two tool_use blocks in the content array. Annotation arrows on each block. Below: code showing iteration over content to collect tool results. Dark background for code, light for explanation.

Here's the multi-tool-call case in code.

Claude can issue multiple tool calls in a single response turn. When this happens, all the `tool_use` blocks appear together in the content array. Your code must process all of them before sending the next request.

```python
tool_results = []

for block in response.content:
    if block.type == "tool_use":
        result = execute_tool(block.name, block.input)
        tool_results.append({
            "type": "tool_result",
            "tool_use_id": block.id,  # Must match Claude's request ID
            "content": result
        })

# All results go back in a single user message
messages.append({
    "role": "user",
    "content": tool_results
})
```

Don't send partial results. Don't process tools one at a time with individual API calls. Process all tool calls from a single response in one batch, then send one combined user message. Now let's lock in why that combined message has to be a USER message.

## SLIDE 8: Tool Results in the Conversation History

**Visual**: Conversation history timeline diagram. Shows the growing messages array across three turns. Turn 1: user + assistant (tool_use). Turn 2: user (tool_result). Turn 3: assistant (tool_use or end_turn). Each message labeled with its role and type. Arrows showing continuation.

Now let's look at the conversation history pattern itself.

The conversation history is how Claude maintains context across an agentic loop. Every message matters. Claude uses the full history to understand what it's already tried, what the results were, and what to do next.

[click]

The pattern looks like this: a user message — the initial request — followed by an assistant message containing tool_use blocks, followed by a user message containing the corresponding tool results, followed by the next assistant response.

This alternating pattern — user, assistant, user, assistant — must be maintained. The API will reject requests that violate turn order. The tool results are framed as user messages because they represent information coming *from* the external environment *to* Claude. ## SLIDE 9: Exam Tip

**Visual**: Amber callout box. Title: "Exam Tip". Two contrasting bullets: wrong pattern (tool results sent as assistant message) vs correct (sent as user message).

Here's the exam tip that closes this lecture.

The exam will test whether you know the correct message role for tool results. Tool results go in **user** messages — not assistant messages.

This trips candidates up because intuitively, "I just ran Claude's tool, so I'm sending back to Claude" feels like the assistant providing output. But the message structure is from Claude's perspective: user messages are what Claude receives from the outside world.

A second exam trap: sending incomplete tool results (only some of the batch) and expecting Claude to work with partial information. Always send all tool results in one user message before calling the API again. Almost-right is the whole trap — and "assistant message holding a tool_result" is exactly the kind of distractor that reads plausible until you know the contract. Last up: the takeaways to lock in.

## SLIDE 10: Key Takeaways

**Visual**: Clean bullet list on light background. Title: "tool_use vs end_turn Control Flow".

Here are the takeaways to carry into 3.3.

- `"tool_use"` path: extract blocks → execute tools → append both assistant msg AND tool results → loop
- `"end_turn"` path: do not loop — inspect content to understand completion state, then return
- Tool results belong in **user** messages (not assistant messages)
- Multiple tool calls in one response → process all, send one combined user message
- Model-driven routing: Claude decides tool order; use for flexible workflows
- Programmatic enforcement: your code enforces order; use for hard constraints (safety, workflow requirements)
