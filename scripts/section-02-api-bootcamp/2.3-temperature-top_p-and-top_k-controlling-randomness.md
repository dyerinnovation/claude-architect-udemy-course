## SLIDE 1: Why Does Claude Sometimes Give Different Answers to the Same Question?

**Visual**: Two side-by-side response bubbles for the identical prompt: "Write a tagline for a coffee shop." Left bubble shows a bland, predictable response. Right bubble shows a creative, surprising response. Below both, a dial graphic ranges from "Deterministic" on the left to "Creative" on the right, with a slider in the middle.

Ask Claude the same question twice.

Sometimes you get the same answer. Sometimes you don't.

That's not a bug — it's a feature you control.

Three parameters govern how creative or predictable Claude's outputs are: `temperature`, `top_p`, and `top_k`.

Most developers only learn enough to set temperature and move on.

But the exam will test whether you know *when* to use each setting — and why. This is classic almost-right territory: `temperature=0` looks like the "safe" answer for a creative-writing scenario, and it's wrong.

Let's build a clear mental model.

---

## SLIDE 2: Temperature — The Main Dial

**Visual**: A probability distribution graph. X-axis shows token options ranked by likelihood. Y-axis shows probability. Two overlapping curves: a tall, narrow "Temperature 0" peak focused on one token, and a flat, wide "Temperature 1.0" curve spread across many tokens. Labels point to each curve.

Temperature controls how Claude samples from its probability distribution. At every step, Claude has a ranked list of possible next tokens, and temperature reshapes that distribution before sampling.

At `temperature=0`, the distribution is collapsed to a spike. Claude almost always picks the highest-probability token. The output is highly deterministic — you'll get the same answer most of the time.

At `temperature=1.0`, the distribution is flat and spread out. Lower-probability tokens get a real chance to be selected. The output is varied, surprising, and creative.

The default is typically around `1.0` for most Claude models. For production use, you almost always want to set it explicitly.

## SLIDE 3: Temperature in Practice — Code vs. Creative Writing

**Visual**: Two Python code blocks side by side. Left block is labeled "Code Review — use low temperature." Right block is labeled "Marketing Copy — use high temperature." Each block shows the same `client.messages.create()` structure with different temperature values circled.

Here's the pattern you need to memorize for the exam. First, the low-temperature side. For code review, extraction, and classification — anywhere you want the same correct answer every time — you set `temperature=0`. Deterministic. Same input gives you the same output. This is the right call for Scenario 6 — Structured Data Extraction — and for any code-generation task.

```python
import anthropic
client = anthropic.Anthropic()

# LOW temperature — for tasks requiring accuracy and consistency
code_review_response = client.messages.create(
    model="claude-sonnet-4-6",
    max_tokens=1024,
    temperature=0,        # Deterministic: same input → same output
    messages=[{
        "role": "user",
        "content": "Review this Python function for bugs: def add(a, b): return a - b"
    }]
)

# HIGH temperature — for tasks requiring creativity and variation
creative_response = client.messages.create(
    model="claude-sonnet-4-6",
    max_tokens=1024,
    temperature=1.0,      # Creative: varied, unexpected output
    messages=[{
        "role": "user",
        "content": "Write three different taglines for an artisan coffee shop."
    }]
)
```

[click]

Now the high-temperature side. For brainstorming, creative writing, marketing copy, story generation — anywhere you want variety and originality — you set temperature to `0.7` or `1.0`. Same model, same SDK call, different parameter. If a candidate ran the coffee-shop tagline prompt at `temperature=0`, all three taglines would come back nearly identical. That defeats the purpose. Match the temperature to the task.

## SLIDE 4: top_p — Nucleus Sampling

**Visual**: Another probability distribution graph. This time, tokens are sorted by probability. A vertical dotted line cuts off the distribution at the point where cumulative probability reaches a set value (e.g., 0.9). The tokens to the left of the line are inside the "nucleus." Tokens to the right are grayed out and labeled "excluded."

`top_p` is a different approach to controlling randomness — also called nucleus sampling. Instead of reshaping the full distribution, it trims it by cumulative probability. Three settings tell the story.

[click]

Start at `top_p = 1.0`. No trimming at all — every token in the distribution remains eligible for sampling. This is the default, the "off" setting.

[click]

Dial down to `top_p = 0.9`. Now Claude only considers tokens whose cumulative probability totals 90 percent. The long tail of unlikely options gets excluded entirely — no matter what temperature says.

[click]

Push it to `top_p = 0.5` and you're aggressively focusing on the most likely candidates only. The practical difference from temperature: `top_p` controls the *size of the candidate pool*, while `temperature` controls the *shape of probabilities within that pool*.

---

## SLIDE 5: top_k — Hard Limit on Candidates

**Visual**: A ranked list of ten tokens by probability. The top three are highlighted in green, labeled "top_k=3 — only these are considered." The remaining seven are grayed out. A callout box notes: "Simple. Blunt. Useful for tight control."

`top_k` is the simplest of the three randomness controls. Three things to lock in.

[click]

First — `top_k = N` means Claude only considers the N highest-probability tokens at each step. Set `top_k=5` and the candidate pool is exactly five tokens. It doesn't care about cumulative probability — it's a hard count.

[click]

Second — `top_k = 1` is equivalent to greedy decoding. Claude always picks the single most likely token. Maximum determinism, no exploration at all.

[click]

Third — how they differ. Temperature reshapes the probabilities. `top_p` trims the candidate pool by cumulative probability. `top_k` trims by count. In practice, Anthropic recommends adjusting only one of these at a time — for most use cases, `temperature` alone is sufficient.

## SLIDE 6: Exam Tip

**Visual**: Amber callout box. Title: "Exam Tip". Icon: target/bullseye. Text: "Low temperature is not always 'better' — match the parameter to the task."

Exam Tip time. The headline — low temperature is not always "better". Two callouts spell out the trap and the signal.

[click]

First, the distractor pattern. Assuming `temperature=0` produces the highest-quality output for *all* tasks, and selecting it as the default in every scenario. That's wrong. Temperature 0 is correct for deterministic tasks — code generation, data extraction, classification, factual Q&A. It is not correct for everything.

[click]

Second, the exam signal. A scenario that says "generate ten different product name ideas" is asking for creative output. At `temperature=0` you'd get ten nearly identical suggestions, which defeats the purpose. Scenario 6 — Structured Data Extraction — is where low temperature wins. Scenario 1's creative redirects are where it loses. Match the parameter to the task.

## SLIDE 7: Key Takeaways

**Visual**: Clean bullet list on light background. Title: "What to Remember".

Four things to remember from this lecture.

[click]

First — `temperature`. It reshapes the probability distribution at each token step. `0` is near-deterministic, `1.0` is highly varied. For the exam, match it to task type: code and extraction take low, creative work takes high.

[click]

Second — `top_p`, also known as nucleus sampling. It limits the candidate pool to tokens whose cumulative probability hits the threshold. `top_p=0.9` excludes the long tail of unlikely tokens.

[click]

Third — `top_k`. It's a hard count limit on candidate tokens. `top_k=1` is greedy decoding, always picking the single most likely token.

[click]

Fourth — adjust one at a time. Anthropic recommends `temperature` alone for most use cases. Stacking all three without intent produces unpredictable results.
