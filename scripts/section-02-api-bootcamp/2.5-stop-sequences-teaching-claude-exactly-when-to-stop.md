## SLIDE 5: How Stop Sequences Work

Now let's look at how stop sequences actually behave at runtime. The stop sequences parameter takes an array of strings.

[click]

On the left, the flow. Claude generates tokens left to right. The API is watching for any of your stop strings. The moment one matches — the wall — generation halts. Everything BEFORE the wall is returned to you. The wall itself is never generated.

[click]

On the right, the mechanics. You pass up to 8,191 stop sequences as an array. Any exact match halts generation. The matched string is omitted from the response body. To verify, check response dot stop reason is "stop sequence" and response dot stop sequence tells you which string matched. Those two fields are your confirmation the stop worked. ## SLIDE 6: When Stop Sequences Are the Right Tool

**Visual**: A four-item vertical list with icons. Each row has a small icon, a use case label in bold, and a one-line description beneath it. Items: (1) XML tag icon — "Structured extraction: stop at `</answer>` to get clean content", (2) delimiter icon — "Delimited output: stop at `###END###` with no trailing content", (3) dialogue bubble icon — "Multi-turn dialogue: stop at turn boundaries like `\nHuman:`", (4) code block icon — "Code generation: stop at a known end marker like `\n\`\`\`\n`".

Now let's run through where stop sequences shine. Four common scenarios.

[click]

First: structured extraction. You ask Claude to wrap a value in answer tags, then set the stop sequence to the closing tag. You get clean content with no trailing prose.

[click]

Second: delimited output. Pick a marker like triple-hash-END-triple-hash, instruct Claude to emit it when finished, and stop there. No trailing content, no markdown fences.

[click]

Third: multi-turn structured dialogue. If Claude is role-playing both sides, stop at the next speaker's turn boundary — something like newline-Human-colon — so you cleanly capture one turn at a time.

[click]

Fourth: code generation. Stop after the closing fence, so you get exactly one clean code block — no commentary, no follow-up explanation. The common thread across all four: you control the prompt, so you know exactly what stop marker to set. Up next, the same pattern in code.

## SLIDE 7: The Code — Stop Sequences in Practice

**Visual**: Dark-background code editor panel showing the full Python example below with syntax highlighting. Four lines are highlighted: the `stop_sequences` parameter, the `stop_reason` check, the `stop_sequence` field access, and the final `print` of the extracted content. A sidebar annotation reads: "Check both fields — `stop_reason` tells you WHY it stopped, `stop_sequence` tells you WHAT matched."

```python
import anthropic

client = anthropic.Anthropic()

response = client.messages.create(
    model="claude-opus-4-7",
    max_tokens=512,
    # Halt generation the moment Claude outputs this exact string
    stop_sequences=["</answer>"],
    messages=[
        {
            "role": "user",
            "content": (
                "What is the capital of Japan? "
                "Wrap your answer in <answer> tags and nothing else."
            )
        }
    ]
)

# Confirm the stop sequence fired as expected
if response.stop_reason == "stop_sequence":
    matched = response.stop_sequence   # Contains "</answer>"
    # Content is everything inside the tags — the closing tag was never generated
    answer = response.content[0].text.strip()
    print(f"Extracted answer: {answer}")
    print(f"Stopped on: {matched}")
else:
    # Stop reason is "end_turn" — model finished before hitting the sequence
    print(f"Unexpected stop reason: {response.stop_reason}")
```

Here's the full pattern in code.

We import the SDK, instantiate the client, and make a normal messages dot create call.

The one new piece is the stop sequences parameter — an array of strings. The moment Claude emits any one of these exact strings, generation halts.

Our prompt asks Claude to wrap the answer in answer tags. Our stop sequence is the closing answer tag. So Claude will write the answer, write the closing tag, and immediately stop.

[click]

Next, the success path. When stop reason equals "stop sequence", the stop fired as expected.

Response dot stop sequence tells you exactly which string matched — useful when you pass multiple stop sequences.

Response dot content, the first item, dot text is everything Claude generated BEFORE the stop string. The matched string itself was never appended to the body — it's reported in stop sequence, not the text.

[click]

The else branch is what matters in production.

If stop reason comes back as "end turn", Claude finished naturally without ever hitting your marker.

That usually means the prompt didn't produce the expected format — Claude answered without wrapping it in tags.

Always handle both cases or you'll silently drop malformed responses. Next, the case and whitespace traps that catch most candidates.

## SLIDE 8: Case Sensitivity and the Whitespace Traps

**Visual**: A three-column comparison table with a red/green header row. Column headers: "What You Wrote", "What Claude Generated", "Did It Stop?". Rows: (1) `"END"` / `"end"` / red X, (2) `"END"` / `"END"` / green checkmark, (3) `" END"` / `"END"` / red X (space before END in the sequence), (4) `"</Answer>"` / `"</answer>"` / red X. A bold caption below the table: "Stop sequences are exact string literals. Case and whitespace both count."

Now let's look at the case and whitespace traps. Stop sequences are exact string matches. Not regex, not fuzzy, not case-insensitive. Every character must match — including capitalization and whitespace. Here are the four traps candidates hit most often.

[click]

First trap: case mismatch. Your stop sequence is uppercase END. Claude generates lowercase end. No match. Generation continues until something else stops it.

[click]

Second: same uppercase END stop sequence — Claude generates uppercase END. Exact match. Generation halts cleanly. This is the only happy path on the table.

[click]

Third trap: hidden whitespace. Your stop sequence is space-END with a leading space. Claude generates END with no leading space. Different bytes. No match.

[click]

Fourth trap: subtle case difference in an XML tag. Your stop sequence has a capital A in Answer. Claude generates lowercase answer. No match. The fix across all four: use stop sequences where you control the exact casing in the prompt. XML closing tags are ideal because you write them and define the casing yourself. Coming up next, the cleanest extraction pattern in the API — stop sequences combined with prefills.

## SLIDE 9: Combining Stop Sequences with Prefills

**Visual**: A horizontal flow diagram. Left box (green): "Prefill: `<answer>`" with label "Controls START". Center box (gray): "Claude generates content here". Right box (red): "Stop sequence: `</answer>`" with label "Controls END". A bracket under all three labeled "Exactly what you wanted — nothing more." Below the diagram, a minimal code snippet showing both the prefill message and the `stop_sequences` parameter side by side.

Now let's combine prefills with stop sequences. These two tools are designed to work together.

You've now seen two complementary tools. Prefills control the START of Claude's output. Stop sequences control the END.

Here's how they combine. The top of the call looks normal — model, max tokens, and the stop sequences parameter pointing at the closing answer tag.

```python
response = client.messages.create(
    model="claude-opus-4-7",
    max_tokens=256,
    stop_sequences=["</answer>"],   # stop at closing tag
    messages=[
        {"role": "user", "content": "What is 144 divided by 12?"},
        {"role": "assistant", "content": "<answer>"}   # prefill opening tag
    ]
)
# response.content[0].text is the raw answer, no tags, no commentary
```

[click]

Inside the messages array, two turns. The user asks the question. The assistant turn is the prefill — just the opening answer tag.

That forces Claude to pick up right after the opening tag — there's no preamble, no "Sure, here's the answer." Claude continues from where the prefill left off.

[click]

The result: the response body is exactly the content between the tags.

No opening tag — that was the prefill, which doesn't appear in response dot content.

No closing tag — that was the stop sequence, which is never generated.

Just the answer. This is the cleanest extraction pattern in the Claude API. Memorize it. Up next, the exam tip the writers love to plant for this concept.

## SLIDE 10: Exam Tip

**Visual**: Amber callout box. Title: "Exam Tip". Icon: target/bullseye. Text: "Stop sequences are exact literals — `'END'` and `'end'` are different stop sequences."

Time for the exam tip. The exam writers love this one because the wrong answer feels so natural.

[click]

The trap. Candidates assume stop sequences behave like regex or case-insensitive pattern matching. They set an uppercase stop sequence, watch it fire inconsistently against lowercase output, and assume the API is buggy. It isn't — the assumption is.

[click]

The correct approach. Stop sequences are exact, case-sensitive literals applied to the raw output stream before any post-processing. Whitespace is significant. Use XML closing tags you control in the prompt — you write them, so you define the casing. Always verify the stop fired by checking stop reason equals "stop sequence" and reading response dot stop sequence. A distractor that claims case-insensitive matching looks almost right — that's the whole point of the trap. Last up: the takeaways to lock in.

## SLIDE 11: Key Takeaways

**Visual**: Clean bullet list on light background. Title: "What to Remember".

Four things to hold onto from this lecture.

[click]

First: stop sequences takes up to 8,191 exact string literals. When any one matches Claude's output, generation halts immediately and the matched string is not included in the response body.

[click]

Second: always check stop reason. The value "stop sequence" means your stop fired and the response is bounded. The value "end turn" means Claude finished naturally before hitting your marker — handle both cases or you'll silently drop malformed responses.

[click]

Third: matching is exact and case-sensitive. Whitespace counts. There is no regex, no fuzzy matching. If a single byte differs, the sequence won't fire.

[click]

Fourth: pair stop sequences with prefills for clean bounded extraction. Prefill opens the format, stop sequence closes it. The response body contains exactly what you need — no opening tag, no closing tag, no commentary.
