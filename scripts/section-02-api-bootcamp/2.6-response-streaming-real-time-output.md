## SLIDE 5: What Is Streaming, Actually?

**Visual**: Animated diagram showing a single large box labeled "Full Response (blocking)" above a horizontal pipeline with many small boxes flowing out labeled `text_delta` chunks. Arrow from pipeline to a browser UI rendering text in real time.

Now let's look at what streaming actually is under the hood. Streaming uses a protocol called Server-Sent Events — S S E for short.

Instead of one big HTTP response, the server sends a series of small events over an open connection.

[click]

Each event carries a tiny piece of the response — a few tokens at a time.

Your code reads each event as it arrives and renders it immediately.

[click]

The total time for Claude to generate the full response is the same either way.

What changes is *when you see the first token* — that's called time-to-first-token, or T T F T.

Streaming dramatically reduces T T F T, which is why it *feels* faster even though it isn't. Up next, the six events that show up in every stream, in order.

## SLIDE 6: The Streaming Event Sequence

**Visual**: Vertical timeline with six labeled events in order, each on its own row with a color-coded badge. Rows: `message_start` (blue), `content_block_start` (green), `content_block_delta` (green, repeating), `content_block_stop` (green), `message_delta` (orange), `message_stop` (red). Small annotation next to `message_delta`: "contains stop_reason + usage".

Now the event sequence — memorize this, the exam tests it. When you open a streaming request, you always see events in this exact order.

Message start comes first — it carries message metadata like the model name and message ID.

[click]

Then content block start signals that a new block of content is beginning.

For a text response, this means a text block is opening.

[click]

Content block delta is the workhorse — you'll receive dozens or hundreds of these.

Each one carries a small chunk of text in a field called text delta.

[click]

Content block stop closes the block when it's finished.

[click]

Then message delta arrives — this is important for the exam.

It carries stop reason and the final usage statistics.

[click]

Finally, message stop signals the stream is completely done.

Memorize this sequence. The exam tests it. Coming up next, how to consume a stream in code with the SDK's easy helper.

## SLIDE 7: Streaming in Python — The SDK Way

**Visual**: Code editor panel on dark background with Python syntax highlighting. A second panel on the right shows terminal output with text appearing line by line, simulating live streaming output.

```python
import anthropic

client = anthropic.Anthropic()

# The SDK's stream() context manager handles SSE for you
with client.messages.stream(
    model="claude-opus-4-7",
    max_tokens=1024,
    messages=[{"role": "user", "content": "Explain REST APIs in plain English."}]
) as stream:
    # text_stream yields each text chunk as a plain string
    for text in stream.text_stream:
        print(text, end="", flush=True)  # flush=True ensures immediate output

# After the context exits, the final message is available
final_message = stream.get_final_message()
print(f"\n\nStop reason: {final_message.stop_reason}")
print(f"Input tokens: {final_message.usage.input_tokens}")
```

Now let's look at how the SDK makes streaming easy. We'll start with the eighty-percent case.

This first chunk is the call setup — almost identical to a regular messages dot create call.

The difference is messages dot stream instead of messages dot create, wrapped in a with block. The SDK's stream context manager abstracts the S S E protocol entirely for you.

[click]

Inside the with block, stream dot text stream is a convenience iterator.

It yields only the text deltas — just the strings, nothing else.

You don't have to parse raw S S E events or worry about event types. This is the eighty-percent case for chat UIs: print the chunk, flush stdout, keep going.

[click]

After the with block exits, get final message gives you the complete assembled message.

This is where you read stop reason and token counts — same fields you'd see from a normal blocking call.

The pattern: stream text for the user, then inspect the final message for control flow. Next, the raw-event loop you'll need for tool calls.

## SLIDE 8: Raw Event Streaming — When You Need Control

**Visual**: Code editor panel showing the raw event loop example. Each `event_type` is highlighted in a different color. A callout box points to `input_json_delta` with the note: "Used when streaming tool call arguments".

```python
import anthropic

client = anthropic.Anthropic()

# Use stream() when you need to handle every event type manually
with client.messages.stream(
    model="claude-opus-4-7",
    max_tokens=1024,
    messages=[{"role": "user", "content": "List three benefits of microservices."}]
) as stream:
    for event in stream:
        if event.type == "content_block_delta":
            # text_delta for text, input_json_delta for tool arguments
            if event.delta.type == "text_delta":
                print(event.delta.text, end="", flush=True)
            elif event.delta.type == "input_json_delta":
                # Partial JSON from a tool call — accumulate this
                print(event.delta.partial_json, end="")
        elif event.type == "message_delta":
            # stop_reason is here, not in message_stop
            print(f"\nStop reason: {event.delta.stop_reason}")
```

Now let's look at the raw-event loop — what you reach for when you're streaming tool calls or reacting to event-level metadata mid-stream.

The setup looks identical: same messages dot stream context manager. The difference is what you do inside the with block.

[click]

Instead of iterating text stream, you iterate raw events with "for event in stream".

Content block delta is the workhorse — it fires once per chunk. Inside, event dot delta dot type tells you what kind of chunk: text delta for text, input json delta for tool-call arguments.

Tool arguments arrive as partial JSON strings. You accumulate them across events and parse once the block closes.

[click]

The message delta branch is the one that catches people on the exam.

Stop reason lives HERE — in message delta — not in message stop.

Message stop just signals "the stream is over." All the meaningful end-of-message metadata — stop reason, final usage — arrives in message delta first. Remember that distinction. Up next, the decision framework — when to stream and when not to.

## SLIDE 9: Stream vs. No-Stream — The Decision Framework

**Visual**: Two-column comparison table with a clean header row. Left column: "Use Streaming" with a green checkmark icon. Right column: "Don't Stream" with a red X icon. Each column has four rows of bullet points. Background is light grey with subtle card styling.

Now the decision framework — when streaming is the right tool and when blocking is fine. Two columns. Each with clear triggers.

[click]

Use streaming when a human is on the other end. Chat interfaces, copilots, assistants — anywhere a person is waiting and watching the response build. Long responses benefit most, because the wait without streaming is the longest. Any UX where immediate feedback matters falls in this column.

[click]

Don't stream when your code is consuming the output, not a human. Batch pipelines, classification jobs, automated extraction — you just need the final answer, not a token-by-token feed. Don't stream when you need the complete response before you can do anything with it, like parsing a full JSON structure. The rule of thumb: if a human sees the output in real time, stream it. If a program consumes it after it's complete, don't bother. Coming up next, the exam tip the writers love to plant for streaming.

## SLIDE 10: Exam Tip

**Visual**: Amber callout box. Title: "Exam Tip". Icon: target/bullseye. Text: "Streaming changes delivery, not content. The exam tests perceived latency vs. total latency."

Time for the exam tip on streaming — two pieces here, both common distractor patterns.

[click]

The trap. Thinking that streaming makes Claude generate responses faster, or that it changes what Claude outputs. Neither is true. Streaming is purely a delivery mechanism — the model does the same work in the same amount of time.

[click]

The correct approach. Streaming reduces perceived latency — time-to-first-token — but does not reduce total generation time. Choose streaming for user-facing UX, not for batch pipelines. And the detail that catches candidates: stop reason arrives in the message delta event, NOT in message stop. That message stop distractor is a textbook almost-right trap. ## SLIDE 11: Key Takeaways

**Visual**: Clean bullet list on light background. Title: "What to Remember".

Four things to hold onto from this lecture.

[click]

First: streaming uses Server-Sent Events with a fixed event order. Message start, then content block start, then many content block delta events, then content block stop, then message delta, then message stop. Memorize this — the exam tests it.

[click]

Second: stop reason and usage stats arrive in message delta, not message stop. The message stop event just signals the stream is over. All the meaningful end-of-message metadata lands in message delta first.

[click]

Third: streaming reduces time-to-first-token — perceived latency — but does NOT reduce total generation time. The model does the same amount of work. You just see the first token sooner.

[click]

Fourth: stream for user-facing interfaces, skip it for batch. If a human is watching the response build, stream. If your code is parsing the full response before acting, don't bother.
