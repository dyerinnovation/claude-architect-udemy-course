## SLIDE 1: Claude Can't Do Everything Alone

**Visual**: Diagram showing Claude as a central node with arrows pointing out to labeled external boxes: "Live Weather API", "Database", "Calculator", "File System". Each arrow is labeled "tool call". Simple, clean node-and-arrow diagram on white background.

Here's a constraint that trips up a lot of architects early on.

Claude is a language model — it reasons and generates text.

It cannot look up today's stock price, query your database, or send an email.

Not by itself.

But you can give Claude tools — and Claude will call them when it needs to.

This is how you connect Claude's reasoning to real-world actions and live data.

The mechanism is called tool use, and it is one of the most important API concepts you'll learn in this course. Tool use anchors Domain 1 — twenty-seven percent of the exam — and Domain 2 at eighteen percent. Together that's forty-five percent riding on what we're about to unpack.

## SLIDE 2: Anatomy of a Tool Definition

**Visual**: Annotated JSON object with three colored callout arrows. The first arrow (blue) points to `name` with label "How Claude refers to this tool". The second arrow (green) points to `description` with label "How Claude decides when to use it". The third arrow (orange) points to `input_schema` with label "What arguments Claude must provide". Clean dark code block on the right half of the slide.

Every tool you give Claude has exactly three required fields. Let me show you the JSON shape, then walk through what each field actually does.

[click]

On the left, the raw JSON. A tool is just an object with three top-level keys: `name`, `description`, and `input_schema`. That's the entire surface area. No SDK class, no inheritance, no decorators — just a dict.

[click]

On the right, the meaning of each field. `name` is a snake_case identifier Claude uses when it calls the tool. `description` is critical — Claude's ability to pick the right tool depends entirely on a good description. And `input_schema` is a JSON Schema object — think of it as the function signature: it tells Claude what arguments to provide and which are required.

## SLIDE 3: A Concrete Tool Definition

**Visual**: Full Python code block showing a tool definition dict for a weather lookup function. Reveals in two chunks — first the name+description that tell Claude *when* to call the tool, then the input_schema that tells Claude *what arguments to provide*.

Let's make this concrete with a real example — a weather lookup tool.

First, the top-level shape: `name` and `description`. The name is a snake_case identifier Claude uses when it calls the tool. The description is the most important field on the whole object — Claude reads it to decide *whether* to use this tool. Notice the description tells Claude both what the tool does AND when to use it.

```python
get_weather_tool = {
    "name": "get_current_weather",
    "description": (
        "Retrieves the current weather for a given city. "
        "Use this when the user asks about current weather conditions."
    ),
    ...
}
```

[click]

Next, the `input_schema` — the function signature Claude will fill in. It's standard JSON Schema. `type: "object"`, a `properties` map listing each argument, and a `required` array. The per-property `description` is also read by Claude — it helps Claude understand what value to put in each argument. The `required` array tells Claude which arguments it must always provide; optional fields like `unit` can be omitted when not relevant.

```python
    "input_schema": {
        "type": "object",
        "properties": {
            "city": {
                "type": "string",
                "description": "The city name, e.g. 'San Francisco'"
            },
            "unit": {
                "type": "string",
                "enum": ["celsius", "fahrenheit"],
                "description": "Temperature unit to return"
            }
        },
        "required": ["city"]
    }
```

## SLIDE 4: Sending the Request With Tools

**Visual**: Two-panel layout. Left panel shows a code block making a `messages.create` call with `tools=[get_weather_tool]` and a user message. Right panel shows a simplified response object with `stop_reason: "tool_use"` and a content array containing a `tool_use` block. A large arrow labeled "Claude responds with a tool call" points from left to right.

You pass tools to `messages.create()` using the `tools` parameter.

```python
import anthropic

client = anthropic.Anthropic()

response = client.messages.create(
    model="claude-opus-4-7",
    max_tokens=1024,
    tools=[get_weather_tool],          # Pass your tool definitions here
    messages=[
        {
            "role": "user",
            "content": "What's the weather like in Tokyo right now?"
        }
    ]
)
```

Claude evaluates the conversation and decides whether to call a tool.

If it decides to call one, `stop_reason` in the response will be `"tool_use"`.

That's your signal — Claude is handing control back to you.

It's not done. It's waiting for you to execute the tool and return the result.

## SLIDE 5: Reading the Tool Use Response

**Visual**: Annotated response object as a code block. The `stop_reason` field is highlighted in amber. Inside the `content` array, a `tool_use` block is highlighted with four callout labels: `type: "tool_use"` (blue), `id` (purple, label "Link this to your result"), `name` (green, label "Which function to call"), `input` (orange, label "The arguments — ready to use").

`stop_reason` is the anchor concept for Domain 1. Everything flows from understanding that `tool_use` means the loop continues and `end_turn` means it stops. Hold onto that — Section 3 goes deep on it.

When `stop_reason` is `"tool_use"`, the response `content` array contains a `tool_use` block. Let's look at the shape, then break down the fields.

[click]

On the left, the raw JSON. Notice `stop_reason: "tool_use"` at the top — that's your signal. Inside `content`, a single block with `type: "tool_use"`, an `id`, the `name` of the tool Claude picked, and an `input` dict containing the arguments Claude filled in. In this example, Claude decided to call `get_current_weather` with `city: "Tokyo"` and `unit: "celsius"`.

[click]

On the right, the four fields you need to know. `type` is always `"tool_use"` — that's how you identify the block in the content array. `id` is a unique identifier like `"toolu_01XFb..."` — you echo this back in your result. `name` matches the tool you defined. And `input` is a ready-to-use Python dict — no JSON parsing required, just splat it into your function.

## SLIDE 6: Executing the Tool and Returning the Result

**Visual**: Code block reveals in three chunks, one step at a time. Step 1: extract the tool_use block from content. Step 2: call the actual function. Step 3: build the follow-up message with the tool_result block. The user-message wrapper, tool_result block, and tool_use_id are highlighted with colored underlines.

Here is the pattern for executing the tool and sending the result back — three steps.

Step 1: find the tool_use block in the response content. The content array can contain multiple block types — text blocks, tool_use blocks — so you filter for the one you want. Here we grab the first tool_use block with a generator expression.

```python
# Step 1: find the tool_use block in the response content
tool_use_block = next(
    block for block in response.content if block.type == "tool_use"
)
```

[click]

Step 2: execute your actual function. The beautiful part — Claude has already parsed the arguments into a Python dict on `tool_use_block.input`. You just splat that dict into your function with the double-star operator. No JSON parsing, no manual extraction.

```python
# Step 2: execute your actual function with Claude's arguments
result = get_current_weather(**tool_use_block.input)
```

[click]

Step 3 is the part everyone gets wrong. You send the result back inside a `user` message — never an assistant message. The `tool_result` block goes in the user content array with a `tool_use_id` that matches the id from Claude's tool_use block. That id is what links your result back to the specific call Claude made. Claude then reads the result and generates its final natural-language response.

```python
# Step 3: send the result back as a user message with a tool_result block
followup = client.messages.create(
    model="claude-opus-4-7",
    max_tokens=1024,
    tools=[get_weather_tool],
    messages=[
        {"role": "user", "content": "What's the weather like in Tokyo right now?"},
        {"role": "assistant", "content": response.content},
        {
            "role": "user",
            "content": [
                {
                    "type": "tool_result",
                    "tool_use_id": tool_use_block.id,
                    "content": str(result),
                }
            ],
        },
    ],
)
```

## SLIDE 7: The Request-Response Cycle Visualized

**Visual**: Vertical flow diagram with five labeled steps connected by arrows: (1) "You: user message + tools" → (2) "Claude: tool_use block, stop_reason='tool_use'" → (3) "You: execute function" → (4) "You: user message with tool_result" → (5) "Claude: final response, stop_reason='end_turn'". Each step is color-coded. Steps 1 and 4 are blue (your actions). Steps 2 and 5 are green (Claude's responses). Step 3 is orange (your code).

Let's step back and see the full cycle. Five steps total — three of them yours, two of them Claude's.

[click]

Step one — you. You send Claude a `user` message with the tool definitions attached via `tools=[...]`. That's the request that kicks off the cycle.

[click]

Step two — Claude. Claude evaluates the conversation, decides it needs a tool, and returns a `tool_use` block with `stop_reason: "tool_use"`. That's the handoff: Claude has paused and is waiting for you.

[click]

Step three — you, again. You execute the real function with the arguments Claude provided. Your application does the actual work — calling the API, querying the database, whatever the tool wraps.

[click]

Step four — still you. You send the result back as a `tool_result` block inside a `user` message, with a `tool_use_id` that matches the id from Claude's tool_use block.

[click]

Step five — Claude closes the loop. Claude reads the result and generates the final natural-language response, returning `stop_reason: "end_turn"`. That two-step exchange is the core of the tool-use pattern — and everything in agentic architecture builds on it.

## SLIDE 8: Exam Tip

**Visual**: Amber callout box. Title: "Exam Tip". Icon: target/bullseye. Text: "Tool results go in a USER message — never an assistant message."

The exam will test exactly one structural detail on tool use: where the `tool_result` goes. Let me show you the wrong pattern first, then the only correct one.

[click]

The wrong structure. Candidates put `tool_result` inside the assistant message alongside the original `tool_use` block. They sometimes omit `tool_use_id` entirely, or skip the assistant message when they replay history. All three are exam-bait — they look reasonable to someone who hasn't built this loop, but Claude rejects every one of them.

[click]

The only correct pattern. After receiving a `tool_use` response, append the assistant message (with its `tool_use` content) to the conversation history. THEN append a new `user` message containing a `tool_result` content block with the matching `tool_use_id`. The id is what links your result back to the specific call Claude made — omit it or mismatch it and the conversation falls apart.

**Exam Trap**: Candidates put `tool_result` blocks inside the `assistant` message alongside the `tool_use` block. This is wrong. The assistant message contains the `tool_use` block. Your follow-up goes in a separate `user` message.

**Correct Approach**: After receiving a `tool_use` response, append the assistant message (with its `tool_use` content) to the conversation history. Then append a new `user` message containing a `tool_result` content block with the matching `tool_use_id`. The `tool_use_id` field is mandatory — omitting it or using the wrong value will break the link between call and result.

## SLIDE 9: Key Takeaways

**Visual**: Clean bullet list on light background. Title: "What to Remember".

Four things to hold onto from this lecture.

[click]

First — the three required fields. Every tool needs `name`, `description`, and `input_schema`. That schema is just JSON Schema — `type: "object"`, a `properties` map, and a `required` array.

[click]

Second — pass tools via `tools=[...]` in `messages.create()`. Claude decides whether to call one, based on the conversation and the descriptions you wrote.

[click]

Third — when `stop_reason == "tool_use"`, the response content contains a `tool_use` block with `id`, `name`, and `input`. That's your signal to execute and return.

[click]

Fourth — and this is the exam trap — return results as a `tool_result` block in a `user` message, using `tool_use_id` to link it back. Never an assistant message. That's the one structural rule the exam tests.

- Every tool needs three fields: `name`, `description`, and `input_schema` (a JSON Schema object)
- Pass tools via `tools=[...]` in `messages.create()` — Claude decides whether to call one
- When `stop_reason == "tool_use"`, the response content contains a `tool_use` block with `id`, `name`, and `input`
- Return results as a `tool_result` content block in a `user` message, using `tool_use_id` to link it back
