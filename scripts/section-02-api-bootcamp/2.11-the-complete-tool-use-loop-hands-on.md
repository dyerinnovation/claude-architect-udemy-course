## SLIDE 2: The Loop Structure — Step by Step

**Visual**: Numbered vertical flowchart with six steps. Each step is a distinct colored box with a short label. Step 1: "Initialize messages list" (blue). Step 2: "Send to Claude with tools" (green). Step 3: "stop_reason == 'end_turn'? → Return response" (teal, exit arrow to right). Step 4: "stop_reason == 'tool_use' → Execute ALL tool_use blocks" (orange). Step 5: "Append assistant message to history" (blue). Step 6: "Append user message with ALL tool_results → Go to Step 2" (green, arrow loops back up).

Let's walk through the structure before we look at code.

Step one: initialize your messages list with the user's message.

Step two: send the messages to Claude with your tools attached.

Step three: check `stop_reason`.

If it's `"end_turn"`, Claude is done — return the response to the user.

[click]

If it's `"tool_use"`, there's work to do.

Step four: execute every `tool_use` block in the response content — not just the first one.

Step five: append Claude's full assistant message to your messages list.

Step six: build a single `user` message containing all the `tool_result` blocks, append it, and loop back to step two.

Notice the loop exits only when `stop_reason` is `"end_turn"`.

Everything else is iteration.

## SLIDE 3: Handling Multiple Tool Calls in One Response

**Visual**: Two-panel layout. Left panel shows a Claude response with two `tool_use` blocks in the content array — `tool_use` for `get_weather` and `tool_use` for `get_forecast`. Right panel shows the correct follow-up user message with two `tool_result` blocks inside a single content array. A bold label reads "Both results in ONE user message." A red X appears below a wrong example showing two separate user messages.

This is where many implementations break.

Claude can return multiple `tool_use` blocks in a single response.

That means it wants to call multiple tools before it continues.

[click]

You must execute all of them.

Then you collect all the results and put them in a single `user` message.

Not one message per result — one message with all results.

If you send them as separate messages, the conversation structure breaks.

Claude expects one `tool_result` per `tool_use` id, all in the same turn.

The second entry is Claude's assistant message — it contains the `tool_use` block.

The third entry is your user message — it contains the `tool_result` block.

[click]

If Claude calls tools twice before answering, you'll have six entries.

The assistant messages always contain the reasoning and tool calls.

The user messages after the first one are always your tool results.

## SLIDE 5: Implementation Part 1 — Tools and Dispatcher

**Visual**: Code panel reveals in two chunks. Chunk 1: tool definitions array (two weather tools with name, description, input_schema). Chunk 2: execute_tool dispatcher function that routes by tool name. Eyebrow: "Implementation — part 1". Title: "Tools & Dispatcher".

Here is the complete implementation, split across two slides so you can see it clearly.

First: the tool definitions. Two weather tools — one for current conditions, one for a five-day forecast. Each has a `name`, a `description`, and an `input_schema`. Both take a single required `city` argument. Notice how compact each schema is — for production tools, the schemas grow, but the shape stays the same.

```python
import anthropic

client = anthropic.Anthropic()

# --- Tool definitions ---
tools = [
    {
        "name": "get_current_weather",
        "description": "Get current weather for a city.",
        "input_schema": {
            "type": "object",
            "properties": {"city": {"type": "string", "description": "City name"}},
            "required": ["city"]
        }
    },
    {
        "name": "get_5day_forecast",
        "description": "Get a 5-day weather forecast for a city.",
        "input_schema": {
            "type": "object",
            "properties": {"city": {"type": "string", "description": "City name"}},
            "required": ["city"]
        }
    }
]
```

[click]

Next: the dispatcher. `execute_tool` is your routing layer — it takes a tool name and an inputs dict, and calls the right real function. In this lecture it returns canned strings, but in production this is where you'd hit a weather API, query a database, or run any external integration. Whatever the tool does, the dispatcher's job is to route by name and return a string the loop can hand back to Claude.

```python
def execute_tool(name: str, inputs: dict) -> str:
    """Route tool calls to real implementations."""
    if name == "get_current_weather":
        return f"Currently 22°C and sunny in {inputs['city']}."
    elif name == "get_5day_forecast":
        return f"5-day forecast for {inputs['city']}: sunny all week, highs ~23°C."
    return "Unknown tool."
```

## SLIDE 6: Implementation Part 2 — The Loop

**Visual**: Code panel reveals in three chunks. Chunk 1: function signature, messages initialization, the API call inside `while True`, and the end_turn exit. Chunk 2: collecting tool_use blocks and building tool_result blocks (the dict-comprehension). Chunk 3: the two history appends (assistant then user) plus the entry-point invocation. Eyebrow: "Implementation — part 2". Title: "The Loop".

Now the loop itself — the engine of the agent. Three chunks.

First: the skeleton. Initialize `messages` with the user's question, then enter `while True`. On every iteration you call `messages.create()` with the full history. Then you check `stop_reason`. If it's `end_turn`, Claude is done — return the text and exit the loop. That's the only exit condition.

```python
def run_agent(user_message: str) -> str:
    messages = [{"role": "user", "content": user_message}]

    while True:
        response = client.messages.create(
            model="claude-opus-4-7",
            max_tokens=1024,
            tools=tools,
            messages=messages,
        )

        # Exit condition: Claude is done
        if response.stop_reason == "end_turn":
            return response.content[0].text
```

[click]

Second: the tool execution branch. If `stop_reason` is `tool_use`, you filter the response content for every tool_use block — could be one, could be several. Then you build a parallel list of tool_result blocks: for each tool_use, you call `execute_tool` with its name and input, and wrap the result in a tool_result with the matching `tool_use_id`. That id is the linkage Claude uses to pair results with calls.

```python
        if response.stop_reason == "tool_use":
            tool_use_blocks = [
                b for b in response.content if b.type == "tool_use"
            ]
            tool_results = [
                {
                    "type": "tool_result",
                    "tool_use_id": tu.id,
                    "content": execute_tool(tu.name, tu.input),
                }
                for tu in tool_use_blocks
            ]
```

[click]

Third: append BOTH messages to history before the next API call. The assistant message (containing Claude's tool_use blocks) goes first, then a single user message containing ALL the tool_result blocks. This is the part the exam tests — N tool_use blocks become ONE user message with N tool_result blocks. Then the loop continues, sends the updated history back to Claude, and the cycle repeats until Claude says `end_turn`.

```python
            messages.append({"role": "assistant", "content": response.content})
            messages.append({"role": "user", "content": tool_results})

answer = run_agent("What's the weather in Paris right now, and the forecast?")
print(answer)
```

## SLIDE 7: Why the Loop Terminates

**Visual**: Decision tree diagram. Root node: "Claude responds". Two branches: "stop_reason == 'end_turn'" (left, green, labeled "Return answer — done") and "stop_reason == 'tool_use'" (right, orange, labeled "Execute tools, extend history, loop again"). A subtle note beneath the orange path reads: "Claude controls how many cycles happen."

A question worth asking: what stops this loop from running forever?

Claude does.

After you return a `tool_result`, Claude either calls another tool or generates a final answer.

It chooses based on whether it has enough information to respond.

[click]

In practice, most tool use loops complete in one or two cycles.

For complex research or multi-step tasks, it might take more.

Production systems often add a safety counter — a maximum iteration limit — to prevent runaway loops.

But the fundamental termination guarantee is Claude's own `stop_reason`.

When Claude has what it needs, it returns `"end_turn"`.

## SLIDE 9: Exam Tip

**Visual**: Amber callout box. Title: "Exam Tip". Icon: target/bullseye. Text: "Multiple tool_use blocks require multiple tool_result blocks in ONE user message."

**Exam Trap**: When Claude returns two `tool_use` blocks in one response, candidates send two separate `user` messages — one for each result. This breaks the conversation structure. The exam will present a code snippet with this bug and ask what's wrong.

**Correct Approach**: When Claude's content array contains multiple `tool_use` blocks, collect all results and send them in a single `user` message with a `content` array containing one `tool_result` block per `tool_use` block. Each `tool_result` must have the matching `tool_use_id`. One assistant turn with N tool calls → one user turn with N tool results. Always.

## SLIDE 10: Key Takeaways

**Visual**: Clean bullet list on light background. Title: "What to Remember".

- The agentic loop runs until `stop_reason == "end_turn"` — Claude controls termination
- Append both the assistant message (with `tool_use` blocks) and the tool results (as a `user` message) to history on every cycle
- If Claude returns multiple `tool_use` blocks, execute all of them and return all results in a single `user` message
