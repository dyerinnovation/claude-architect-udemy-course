## SLIDE 4: The Five Core Request Parameters

**Visual**: A Python code block on a dark background. Five parameters highlighted in different colors: `model` in blue, `max_tokens` in orange, `messages` in green, `system` in purple, `temperature` in red. Each has a short label floating beside it.

Every call to `client.messages.create()` shares the same skeleton. There are five parameters you need to know cold.

[click]

`model` tells the API which Claude to use — `claude-sonnet-4-6`, for example.

[click]

`max_tokens` sets the hard ceiling on how many tokens Claude can generate in the response.

[click]

`messages` is the conversation history — an array of turns with roles and content.

[click]

`system` is where you put persistent instructions that apply to the whole conversation.

[click]

`temperature` controls how creative or deterministic the output is. These five parameters are the foundation of everything else in this section.

Now let's see all five wired together in a real request.

## SLIDE 5: A Complete Request, Annotated

**Visual**: Dark-background code editor showing a full `client.messages.create()` call in Python. Each line has a comment on the right side. The `messages` array is expanded to show two items: one with `role: "user"` and one with `role: "assistant"`.

Let's look at a real, complete request — I'll build it up piece by piece.

```python
import anthropic

client = anthropic.Anthropic()  # Uses ANTHROPIC_API_KEY from environment

response = client.messages.create(
    model="claude-sonnet-4-6",   # Which Claude model to use
    max_tokens=1024,                       # Max tokens in the response
    system="You are a helpful assistant.", # Top-level system prompt
    messages=[
        {
            "role": "user",                # Must be "user" or "assistant"
            "content": "What is the capital of France?"
        },
        {
            "role": "assistant",           # Claude's previous turn
            "content": "The capital of France is Paris."
        },
        {
            "role": "user",               # The new question we're asking
            "content": "What is its population?"
        }
    ]
)
```

[click]

We start by importing anthropic and creating a client. The client picks up your `ANTHROPIC_API_KEY` from the environment — no need to pass it explicitly.

[click]

Then we call `client.messages.create()`. Three things at the top level: `model`, `max_tokens`, and `system`. Notice — `system` is a TOP-LEVEL parameter, not a role inside the messages array. We'll come back to this trap in two slides.

[click]

Inside `messages`, we pass the conversation history as an array of turns. Roles strictly alternate between `"user"` and `"assistant"`. You maintain this history every call — Claude has no memory between calls, so everything it knows about the conversation is in this array. One thing to flag now though: in agentic workflows, those user and assistant turns can also carry tool_use and tool_result blocks alongside the plain text — there are a couple of patterns for handling that, and Section 4 covers them in depth. Now let's flip to the response side and dissect what comes back.

## SLIDE 6: The Response Object, Dissected

**Visual**: A formatted JSON object on a light background. Fields are shown in a two-column table: field name on the left, a one-sentence explanation on the right. Highlighted fields: `id`, `type`, `role`, `content`, `model`, `stop_reason`, `stop_sequence`, `usage`.

Now let's look at what comes back.

[click]

Three quick metadata fields at the top: `id`, `type` — which is always 'message' at the top level — and `role`, always 'assistant'. Heads up: inside the content array you'll see `text` or `tool_use` types — we'll cover those in just a moment when we look at content.

[click]

Then the `content` field — and this is the key insight: content is a LIST, not a string. Even simple text responses come wrapped in a content block with `type: text`. This matters because when tool use is involved, you'll see `tool_use` blocks in this list instead.

[click]

Below content, three "why did Claude stop" fields: `model` tells you which model responded, `stop_reason` — which we'll spend a whole slide on next — and `stop_sequence` for custom stop strings.

[click]

And finally `usage` — input and output tokens, billed separately. Log this for cost tracking on every call. Up next, the four values of stop reason in detail.

---

## SLIDE 7: The Four Values of stop_reason

**Visual**: Four numbered cards in a stack. Each card has the stop_reason value as the headline and a one-line explanation. Color cues: green for end_turn, amber for max_tokens, blue for stop_sequence, purple for tool_use.

The `stop_reason` field is one of those small details that separates production-ready code from "works on my machine" code. You'll see four values.

[click]

`end_turn` means Claude finished naturally — the response is complete.

[click]

`max_tokens` means Claude hit the ceiling you set in `max_tokens`. The response may be cut off mid-sentence. In production, you check for this and continue the response with another call if needed.

[click]

`stop_sequence` means a custom stop string you provided was triggered. Used for structured-output workflows.

[click]

`tool_use` means Claude wants to call a tool. The agent loop continues — you execute the tool, append the result, and call back. We'll cover the full tool loop in section 4. The production rule: always inspect `stop_reason` after every call. It's how you branch your agent logic. Up next, the safe code patterns for reading the response.

## SLIDE 8: Reading the Response in Code

**Visual**: Python code snippet on dark background. Shows `response.content[0].text` being accessed. An arrow from the code points to the extracted string. A second snippet shows iterating over `response.content` with a for loop, with a comment "handles multiple content blocks."

Now let's read the response in code. Knowing the structure matters when you go to fetch the data out.

[click]

The quick way: response dot content, the first item, dot text. That grabs the first text block. Works for simple cases — no tool use, single text-block response.

[click]

In production — especially when tool use is in play — you should iterate over `response.content` and check each block's type. This handles multi-block responses cleanly and is the pattern you'll write almost every time.

[click]

Always check stop reason for robustness. If it's `max_tokens`, the response was truncated and you may need to continue it with another call. And `usage` tells you what each call cost in tokens — log this for cost tracking. One more thing before takeaways — the most common exam trap on this topic.

## SLIDE 9: Exam Tip

**Visual**: Amber callout box. Title: "Exam Tip". Icon: target/bullseye. Text: "System is NOT a role — it's a top-level parameter."

Here's the trap you need to watch for on the exam. The most common almost-right answer on this topic is putting the system prompt inside the `messages` array using `role: "system"` — but that pattern doesn't exist in the Claude API.

[click]

That OpenAI-style pattern looks reasonable, but it's wrong. The Claude API only accepts two roles inside `messages`: `"user"` and `"assistant"`. If you see a question showing `{"role": "system", "content": "..."}` inside the messages array, that's the wrong answer.

[click]

The correct pattern: pass `system` as a top-level parameter to `client.messages.create()`, right alongside `model` and `max_tokens`. Almost-right is the whole trap of this exam, and this is a textbook example of it. Last up: the takeaways to lock in.

## SLIDE 10: Key Takeaways

**Visual**: Clean bullet list on light background. Title: "What to Remember".

Four takeaways from this lecture. Hold onto these as we move through the next sections.

[click]

First: every messages dot create call requires `model`, `max_tokens`, and `messages`. The `system` parameter is separate from that array.

[click]

Second: the `messages` array only accepts two roles — `"user"` and `"assistant"`. `"system"` is not a valid role.

[click]

Third: responses return a `content` list of typed blocks — `"text"` for plain responses, `"tool_use"` when tools are involved.

[click]

Fourth: `stop_reason` tells you why generation ended. Always check it in production code to handle truncated responses.
