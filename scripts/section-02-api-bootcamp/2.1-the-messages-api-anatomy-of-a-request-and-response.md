## SLIDE 2: The Five Core Request Parameters

**Visual**: A Python code block on a dark background. Five parameters highlighted in different colors: `model` in blue, `max_tokens` in orange, `messages` in green, `system` in purple, `temperature` in red. Each has a short label floating beside it.

Every call to `client.messages.create()` shares the same skeleton.

There are five parameters you need to know cold.

`model` tells the API which Claude to use — `claude-sonnet-4-6`, for example.

`max_tokens` sets the hard ceiling on how many tokens Claude can generate in the response.

`messages` is the conversation history — an array of turns with roles and content.

`system` is where you put persistent instructions that apply to the whole conversation.

`temperature` controls how creative or deterministic the output is.

These five parameters are the foundation of everything else in this section.

## SLIDE 3: A Complete Request, Annotated

**Visual**: Dark-background code editor showing a full `client.messages.create()` call in Python. Each line has a comment on the right side. The `messages` array is expanded to show two items: one with `role: "user"` and one with `role: "assistant"`.

Let's look at a real, complete request. We start by importing anthropic and creating a client. The client picks up your `ANTHROPIC_API_KEY` from the environment — no need to pass it explicitly.

```python
import anthropic

client = anthropic.Anthropic()  # Uses ANTHROPIC_API_KEY from environment

response = client.messages.create(
    model="claude-sonnet-4-6",   # Which Claude model to use
    max_tokens=1024,                       # Max tokens in the response
    system="You are a helpful assistant.", # Top-level system prompt
    messages=[
        {
            "role": "user",                # Must be "user" or "assistant"
            "content": "What is the capital of France?"
        },
        {
            "role": "assistant",           # Claude's previous turn
            "content": "The capital of France is Paris."
        },
        {
            "role": "user",               # The new question we're asking
            "content": "What is its population?"
        }
    ]
)
```

[click]

Then we call `client.messages.create()`. Three things at the top level: `model`, `max_tokens`, and `system`. Notice — `system` is a TOP-LEVEL parameter, not a role inside the messages array. We'll come back to this trap in two slides.

[click]

Inside `messages`, we pass the conversation history as an array of turns. Roles strictly alternate between `"user"` and `"assistant"`. You maintain this history every call — Claude has no memory between calls, so everything it knows about the conversation is in this array.

## SLIDE 4: The Response Object, Dissected

**Visual**: A formatted JSON object on a light background. Fields are shown in a two-column table: field name on the left, a one-sentence explanation on the right. Highlighted fields: `id`, `type`, `role`, `content`, `model`, `stop_reason`, `stop_sequence`, `usage`.

Now let's look at what comes back.

```python
# The response object looks like this:
{
    "id": "msg_01XFDUDYJgAACzvnptvVoYEL",  # Unique message ID
    "type": "message",                       # Always "message"
    "role": "assistant",                     # Always "assistant"
    "content": [                             # List of content blocks
        {
            "type": "text",                  # Content block type
            "text": "The population of Paris..."
        }
    ],
    "model": "claude-sonnet-4-6",  # Model that responded
    "stop_reason": "end_turn",              # Why Claude stopped
    "stop_sequence": None,                  # Which stop sequence triggered (if any)
    "usage": {
        "input_tokens": 42,                 # Tokens in your request
        "output_tokens": 31                 # Tokens in the response
    }
}
```

The `content` field is a list, not a string. Even a simple text response is wrapped in a content block with `type: text`. This matters because when tool use is involved, you'll see `tool_use` blocks in this list instead.

[click]

Below that, two more fields you'll care about. `stop_reason` tells you WHY Claude stopped — we'll dig into the four values on the next slide. And `usage` tells you what you're being billed for: input tokens and output tokens, broken out separately.

## SLIDE 5: The Four Values of stop_reason

**Visual**: Four numbered cards in a stack. Each card has the stop_reason value as the headline and a one-line explanation. Color cues: green for end_turn, amber for max_tokens, blue for stop_sequence, purple for tool_use.

The `stop_reason` field is one of those small details that separates production-ready code from "works on my machine" code. You'll see four values.

`end_turn` means Claude finished naturally — the response is complete.

`max_tokens` means Claude hit the ceiling you set in `max_tokens`. The response may be cut off mid-sentence. In production, you check for this and continue the response with another call if needed.

`stop_sequence` means a custom stop string you provided was triggered. Used for structured-output workflows.

`tool_use` means Claude wants to call a tool. The agent loop continues — you execute the tool, append the result, and call back. We'll cover the full tool loop in section 4.

The production rule: always inspect `stop_reason` after every call. It's how you branch your agent logic.

## SLIDE 6: Reading the Response in Code

**Visual**: Python code snippet on dark background. Shows `response.content[0].text` being accessed. An arrow from the code points to the extracted string. A second snippet shows iterating over `response.content` with a for loop, with a comment "handles multiple content blocks."

Knowing the structure matters when you go to read the response. The quick way: `response.content[0].text` grabs the first text block. This works for simple cases — no tool use, single text-block response.

```python
# Most common case: access the first text block directly
answer = response.content[0].text
print(answer)

# Safer: iterate over all content blocks
for block in response.content:
    if block.type == "text":
        print(block.text)

# Check why Claude stopped
print(response.stop_reason)   # "end_turn", "max_tokens", "stop_sequence", "tool_use"

# Check token usage
print(f"Input: {response.usage.input_tokens}")
print(f"Output: {response.usage.output_tokens}")
```

[click]

In production — especially when tool use is in play — you should iterate over `response.content` and check each block's type. This handles multi-block responses cleanly and is the pattern you'll write almost every time.

[click]

Always check `stop_reason` for robustness. If it's `max_tokens`, the response was truncated and you may need to continue it with another call. And `usage` tells you what each call cost in tokens — log this for cost tracking.

## SLIDE 7: Exam Tip

**Visual**: Amber callout box. Title: "Exam Tip". Icon: target/bullseye. Text: "System is NOT a role — it's a top-level parameter."

**Exam Trap**: Passing the system prompt as a message in the `messages` array using `role: "system"` — this is not valid in the Claude API.

**Correct Approach**: The `system` parameter is always top-level in `client.messages.create()`, never inside the `messages` array. The only valid roles in `messages` are `"user"` and `"assistant"`.

If you see a question showing `{"role": "system", "content": "..."}` inside the messages array, that is the wrong answer. That pattern comes from OpenAI's API and does not work here. Almost-right is the whole trap of this exam — and this is a textbook example.

## SLIDE 8: Key Takeaways

**Visual**: Clean bullet list on light background. Title: "What to Remember".

- Every `messages.create()` call requires `model`, `max_tokens`, and `messages` — the `system` parameter is separate from the array
- The `messages` array only accepts two roles: `"user"` and `"assistant"` — `"system"` is not a valid role
- Responses return a `content` list of typed blocks — always `"text"` for plain responses, `"tool_use"` when tools are involved
- `stop_reason` tells you why generation ended — always check it in production code to handle truncated responses
