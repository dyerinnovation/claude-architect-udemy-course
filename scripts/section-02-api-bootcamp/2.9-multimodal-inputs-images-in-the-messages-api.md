## SLIDE 4: The Content Block Model

**Visual**: Two side-by-side code boxes. Left: a simple string message `"content": "Hello"`. Right: an expanded array `"content": [{"type": "text", "text": "Hello"}]`. An arrow labeled "Same thing" connects them. Both are styled with syntax highlighting.

Let's look at the content-block model — the foundation everything multimodal builds on.

You already know that `content` in the Messages API can be a plain string.

But it doesn't have to be — and that flexibility is the whole basis for sending images.

[click]

Here's the string form on the left. Simple — just a `"content"` field with a string value. This is what you've been writing all along.

[click]

And here's the content-block form on the right. `"content"` is now an array of objects. Each block has a `type` field telling Claude what kind of content it is — `"type": "text"` for text, `"type": "image"` for images. The order matters: Claude reads them in sequence, top to bottom. That's the door that opens for multimodal. Next, the two source types for image blocks.

## SLIDE 5: Two Ways to Provide an Image

**Visual**: Two stacked cards side by side. Left card labeled "Base64" shows a truncated base64 string with fields: `type: "base64"`, `media_type: "image/jpeg"`, `data: "..."`. Right card labeled "URL" shows fields: `type: "url"`, `url: "https://..."`. Both cards have subtle background tints — blue for base64, green for URL.

Let's look at the two source types for image content blocks, side by side.

[click]

First — base64. You encode the image bytes as a base64 string and provide `media_type` to tell Claude the image format. The valid media types are `"image/jpeg"`, `"image/png"`, `"image/gif"`, and `"image/webp"`. Use base64 when the image is private or stored locally.

[click]

Second — URL. You provide a public HTTPS URL, and Claude fetches the image at inference time. Use URL when the image is already publicly accessible and stable. No `media_type` needed here — the server returns it. Up next, the full Python example end-to-end.

## SLIDE 6: Sending an Image — Python Code Example

**Visual**: Full-width Python code block on a dark background with syntax highlighting. Reveals in three chunks: imports + client, base64 encoding step, then the API call with image and text blocks.

Let's put it all together in a complete Python example that encodes a local image as base64 and sends it with a question. Walking through it in three pieces.

First, the imports and the client. Standard `anthropic` plus Python's built-in `base64` module. The client picks up your API key from the environment, same as every other call we've seen in this section.

```python
import anthropic
import base64

client = anthropic.Anthropic()
```

[click]

Next, the encoding step. You open the image file in binary mode, read the bytes, base64-encode them, and decode to a UTF-8 string. That UTF-8 string is what you'll hand to the API — Claude expects base64 as text inside JSON, not raw bytes.

```python
# Read the image file and encode it as base64
with open("diagram.png", "rb") as image_file:
    image_data = base64.standard_b64encode(image_file.read()).decode("utf-8")
```

[click]

Now the API call — and this is the part the exam tests. The `content` field is an array. The first block is `"type": "image"`, with a `source` object containing all three required fields: `type`, `media_type`, and `data`. The second block is the text question. Order matters: Claude reads top to bottom, so the image lands first, then the question about it.

```python
response = client.messages.create(
    model="claude-opus-4-7",
    max_tokens=1024,
    messages=[
        {
            "role": "user",
            "content": [
                {
                    "type": "image",
                    "source": {
                        "type": "base64",
                        "media_type": "image/png",
                        "data": image_data,
                    },
                },
                {"type": "text", "text": "What does this diagram show?"},
            ],
        }
    ],
)
```

That's the structural pattern. Next, let's zoom out and look at *what* Claude can actually do with images you send.

## SLIDE 8: Exam Tip

**Visual**: Amber callout box. Title: "Exam Tip". Icon: target/bullseye. Text: "Images are content blocks — not a separate parameter."

The exam will test exactly one structural detail on multimodal: where images live in the request. Let's look at the trap, then the only correct pattern.

[click]

The distractor patterns. Candidates pass images as a standalone parameter like `image=` outside `messages`. Or they paste the image URL into the system prompt. Or they hand in a base64 source without a `media_type`. All three look plausible — none of them work.

[click]

The only correct pattern. Images go inside the `content` array of a user message as a content block with `"type": "image"` and a `"source"` object. The `source` must include `type` (`"base64"` or `"url"`), `media_type` for base64, and either `data` or `url`. That structural shape is the answer to every multimodal question on the exam.

**Exam Trap**: Candidates pass images as a standalone parameter like `image=` or as a top-level key outside `messages`. This is not how the API works.

**Correct Approach**: Images go inside the `content` array of a message as a content block with `"type": "image"` and a `"source"` object. The `source` must include `type` (`"base64"` or `"url"`), `media_type` (e.g. `"image/jpeg"`), and either `data` or `url`. A missing `media_type` on a base64 source is another common trap — it is required, not optional. Distractors that invent an `image=` parameter are plausible in other SDKs — that's exactly what makes them almost-right.
