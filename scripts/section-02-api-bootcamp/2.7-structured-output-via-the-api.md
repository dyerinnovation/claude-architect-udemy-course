## SLIDE 4: When JSON From Claude Breaks Your Pipeline

**Visual**: Dark code panel showing a broken JSON object: opening brace, three valid string/number fields, a trailing comma after the third field, then the closing brace. Annotation panel below the code: "JSONDecodeError: Expecting property name enclosed in double quotes. One malformed response. One crashed pipeline. You need a guarantee — not a retry loop."

Here's what "usually works" looks like in production. This snippet looks fine at a glance. Three fields, a closing brace.

The problem is the trailing comma on line 4 — Python's json dot loads refuses it. JavaScript's JSON dot parse refuses it. Your pipeline crashes the moment this response hits your parser.

[click]

And the error is exactly what you'd expect — JSONDecodeError. One trailing comma. One markdown fence. One friendly "Sure, here's your JSON:" preamble. Any of these breaks parsing instantly. The fix isn't more retry logic. The fix is reaching for an API feature that gives you a structural guarantee — not a best-effort hint. Coming up next, the three approaches ranked by reliability.

## SLIDE 6: The Gold Standard — Tool Use for Structured Output

**Visual**: Code editor with Python syntax highlighting. A callout arrow points to `tool_choice={"type": "any"}` with the annotation "Forces Claude to call a tool — no plain text allowed". A second callout points to the `input_schema` block with the annotation "Your schema lives here".

```python
import anthropic

client = anthropic.Anthropic()

# Define your schema as a "fake" tool — Claude must call this
extraction_tool = {
    "name": "extract_order",
    "description": "Extract structured order data from the user message.",
    "input_schema": {
        "type": "object",
        "properties": {
            "order_id": {"type": "string", "description": "The order identifier"},
            "customer_name": {"type": "string"},
            "total_amount": {"type": "number"},
            "status": {"type": "string", "enum": ["pending", "shipped", "delivered"]}
        },
        "required": ["order_id", "customer_name", "total_amount", "status"]
    }
}

response = client.messages.create(
    model="claude-opus-4-7",
    max_tokens=1024,
    tools=[extraction_tool],
    tool_choice={"type": "any"},  # Force Claude to call a tool
    messages=[{"role": "user", "content": "Order #A123, Jane Smith, $49.99, shipped."}]
)

# The structured data is always in content[0].input
order_data = response.content[0].input
print(order_data)
```

Here's the gold-standard pattern in code.

The key insight: you're defining a tool purely to receive structured output.

Claude isn't actually calling an external function — you're using the tool-calling mechanism as a schema enforcement layer.

This first chunk shows the tool definition. Notice input schema — that's a standard JSON Schema object. Properties, types, enums, required fields. Whatever you put in here is what Claude must produce.

[click]

Next, the create call. Two parameters do the work here.

Tools equals the extraction tool array — that registers the tool with the request.

Tool choice equals type "any" is critical. It forces Claude to call ONE of your tools — Claude cannot respond with plain text. Without this, Claude might still answer conversationally and skip the tool.

[click]

Finally, reading the response. Response dot content, the first item, dot input gives you the structured data as a native Python dict — already validated against your schema.

The SDK rejects malformed output before it ever reaches your code. That's the guarantee. No try-except around json dot loads. No retry loops for trailing commas. Schema conformance is enforced server-side. Coming up next, the three fields you'll read on every tool-use response.

## SLIDE 7: Reading the Tool Use Response

**Visual**: Annotated JSON response object. `stop_reason` is highlighted in yellow with label "Always 'tool_use' when a tool was called". `content[0].type` is highlighted in green with label "'tool_use'". `content[0].input` is highlighted in blue with label "Your validated, schema-conformant data".

```python
# After the create() call from the previous slide...

# stop_reason tells you Claude called a tool, not finished naturally
print(response.stop_reason)          # "tool_use"

# The content block type is "tool_use"
print(response.content[0].type)      # "tool_use"

# The tool that was called
print(response.content[0].name)      # "extract_order"

# The validated, schema-conformant data — this is what you want
structured_data = response.content[0].input
print(type(structured_data))         # <class 'dict'> — already parsed, not a string
print(structured_data["order_id"])   # "A123"
print(structured_data["status"])     # "shipped"
```

Now let's read a tool-use response field by field. Three quick fields tell you what just happened.

Response dot stop reason is always "tool use" when a tool was called — not "end turn". This is a common exam question. Know it cold.

Response dot content, the first item, dot type confirms the block is a "tool use" block.

Response dot content, the first item, dot name tells you WHICH tool Claude called — important when you registered more than one.

[click]

Now the payload itself. Response dot content, the first item, dot input is the structured data — already a Python dict, parsed by the SDK.

You're not doing json dot loads on a string. You get a native object you can index into directly — structured data, key order id, gives you the order ID as a string, no parsing step in between.

That's what makes this pattern feel different from "just ask for JSON." There's no string-to-dict conversion in your code. The SDK has already done it, with schema validation included. Up next, the silver-medal approaches that don't give you that guarantee.

## SLIDE 8: The Silver Medal — `response_format` and System Prompt JSON

**Visual**: Split code panel. Left side shows a system prompt approach. Right side shows the `response_format` parameter. A red warning badge on both reads: "No schema enforcement — structure is Claude's best effort."

```python
# APPROACH 2: response_format parameter — valid JSON, but no schema
response = client.messages.create(
    model="claude-opus-4-7",
    max_tokens=1024,
    messages=[{
        "role": "user",
        "content": "Extract the order details as JSON: Order #B456, Tom Lee, $29.00, pending."
    }]
)
# Claude will output JSON syntax, but the shape is up to Claude
raw_json = response.content[0].text  # Still a string — you must parse it

# APPROACH 3: System prompt instruction — most flexible, least enforced
system = """You are a data extractor. Always respond with valid JSON matching this schema:
{"order_id": string, "customer_name": string, "total_amount": number, "status": string}
Never include any text outside the JSON object."""

response = client.messages.create(
    model="claude-opus-4-7",
    max_tokens=1024,
    system=system,
    messages=[{"role": "user", "content": "Order #C789, Sara Kim, $99.50, delivered."}]
)
# Usually works. But Claude could add a markdown code fence, or a preamble sentence.
```

Now the runners-up. Two cleaner-looking approaches that still don't give you a guarantee.

Approach 2 — the response format parameter — tells Claude to output valid JSON syntax. No trailing commas, no markdown fences. But it doesn't enforce YOUR specific schema. The shape is whatever Claude decides.

You still get a string back at response dot content, the first item, dot text. You still call json dot loads. You still need to validate the shape yourself after parsing.

[click]

Approach 3 — system-prompt instruction — is the most flexible, least enforced option.

You describe the schema in plain English in your system prompt. Usually Claude follows it. But once in a while, you get a markdown code fence, or a preamble sentence like "Sure, here's the JSON," or a missing field.

It's fine for quick extractions in low-stakes pipelines, but not for anything production-critical. When schema compliance matters, reach for tool use — not these. Coming up next, the distinction the exam tests directly.

## SLIDE 9: What Tool Use Guarantees — And What It Doesn't

**Visual**: Two-column table with a bold header row. Left column header: "Tool Use GUARANTEES" (green checkmark). Right column header: "Tool Use Does NOT Guarantee" (red X). Left column rows: "Syntactically valid JSON", "Schema-conformant field names", "Correct data types per schema". Right column rows: "Factually correct values", "Data that actually exists in the source", "Freedom from hallucination".

Now the most important distinction in this lecture — and the exam tests it directly.

Tool use eliminates *syntax errors*.

The JSON will be valid. The fields will match your schema. The types will be correct.

[click]

But tool use cannot prevent *semantic errors*.

If you ask Claude to extract an order ID that doesn't exist in the document, it might hallucinate one.

The hallucinated order ID will be a perfectly valid string in the right field.

Schema enforcement is not fact enforcement.

[click]

The mental model: tool use is a syntax and structure guarantee, not a truth guarantee.

For critical pipelines, you still need application-level validation of the *values*. Up next, the exam tip the writers love to plant around this exact distinction.

## SLIDE 10: Exam Tip

**Visual**: Amber callout box. Title: "Exam Tip". Icon: target/bullseye. Text: "Tool use guarantees schema conformance — not semantic correctness. The exam tests this distinction specifically."

Time for the exam tip on structured output. The exam writes this trap specifically because the wrong answer feels intuitive.

[click]

The trap. Choosing tool use for structured output because you believe it eliminates *all* errors in the output — including wrong values or hallucinated data. That overreach is the trap.

[click]

The correct approach. Tool use with tool choice "any" guarantees syntactically valid, schema-conformant JSON — it eliminates parse errors and field-shape errors. It does NOT guarantee values are correct or hallucination-free. When an exam question asks "What does tool use guarantee?" the answer is schema conformance, not factual accuracy. And remember: stop reason is "tool use" — never "end turn" — whenever Claude calls a tool. Last up: the takeaways to lock in.
