## SLIDE 4: What the System Parameter Actually Is

**Visual**: Diagram of a `messages.create()` call rendered as a layered structure. The `system` parameter floats above the `messages` array like a header. An annotation reads "applies to all turns." The messages array below shows multiple user/assistant alternating turns with no repeated instructions.

To understand `system`, picture the two halves of an API call side by side. Two terms first, so the rest of the lecture lands cleanly: the **system parameter** is the API field — a top-level argument to messages dot create, lowercase, named `system`. The **system prompt** is the text you put on that field — the persona, the rules, the standing brief Claude reads before any conversation begins. The parameter holds the prompt.

[click]

On the left, the visualization. The `system` parameter sits above the `messages` array as a standing brief — Claude reads it before the conversation begins, and it applies to every turn. The array itself is just user-and-assistant turns, with no instructions repeated inside.

[click]

On the right, the three properties to lock in. It's a top-level field in messages dot create — outside the `messages` array. It's a standing brief — Claude reads it before the conversation begins. And it's persistent — it applies automatically across every turn. Write it once, apply it everywhere. Next up, what correct usage actually looks like in code.

## SLIDE 5: The Right Way — System Parameter in Action

**Visual**: Dark-background Python code editor. The `system` parameter is highlighted with a yellow border. The `messages` array contains only user and assistant turns — no instructions repeated. A green checkmark badge in the top-right corner of the code block.

Here's what correct usage looks like. We start the usual way — import anthropic, create the client. The client picks up your API key from the environment.

```python
import anthropic

client = anthropic.Anthropic()

# System prompt defined once — applies to every turn
SYSTEM_PROMPT = """You are Aria, a friendly customer support agent for SkyLine Airlines.
You only answer questions about flights, baggage, and reservations.
If asked about anything else, politely redirect the customer."""

response = client.messages.create(
    model="claude-sonnet-4-6",
    max_tokens=1024,
    system=SYSTEM_PROMPT,       # Top-level parameter — NOT in messages array
    messages=[
        {
            "role": "user",
            "content": "Hi, I need to change my seat on flight SK442."
        }
    ]
)

print(response.content[0].text)
```

[click]

Next we define the system prompt itself — a triple-quoted string we'll reuse on every call. Aria's persona, scope, and redirect rule are established here, once, in one place. Notice it's a plain Python constant — nothing API-specific yet. You can rebuild this from a database, swap personas at runtime, whatever you need.

[click]

Now the call itself. The `system` parameter sits alongside `model` and `max_tokens` at the top level — not inside `messages`. The messages array holds only the user turn. Every subsequent turn in this conversation will operate under Aria's rules, and you will never repeat the system prompt in the messages array. Up next, the broken version of the same idea — instructions buried in a user message.

## SLIDE 6: The Wrong Way — Instructions in the User Message

**Visual**: Dark-background Python code with a red X badge in the top-right corner. The first message in the `messages` array has both instructions and a user question crammed together. An annotation arrow points to the `role: "user"` line with the label "this role is for user input, not instructions."

Now let's look at the pattern that breaks things.

```python
# WRONG: Embedding instructions inside the first user message
response = client.messages.create(
    model="claude-sonnet-4-6",
    max_tokens=1024,
    # No system parameter
    messages=[
        {
            "role": "user",
            # Instructions mixed into a user turn — this is the mistake
            "content": """You are Aria, a customer support agent for SkyLine Airlines.
Only answer questions about flights, baggage, and reservations.

Hi, I need to change my seat on flight SK442."""
        }
    ]
)
```

[click]

This works for exactly one turn. When the conversation continues, you have a problem.

The instructions are now buried in the history as a user message. They're not guaranteed to influence future turns the same way a real system prompt would.

And here's the critical difference: you're responsible for replaying the full `messages` array on every API call. If you truncate the history to save tokens, you lose the instructions entirely.

A system prompt, by contrast, always comes through — it's never truncated from the history. Next up, what this looks like across three actual turns.

## SLIDE 7: Building the Multi-Turn Chat Function

**Visual**: `<CodeBlockSlide>` Python — the `chat()` function builds across five chunks. Chunk 0 a brief context comment; chunks 1-4 reveal one logical block each (history list, function signature + user-turn append, the API call with `system=`, capture-and-return).

Let's see this play out across multiple turns. The chat function we're about to build takes one user message, calls Claude with the persistent system prompt, and tracks the full conversation history. Here it is in five logical pieces.

```python
# Conversation history is just a list of dicts — that's the entire memory
conversation_history = []

def chat(user_message):
    conversation_history.append({
        "role": "user",
        "content": user_message
    })

    response = client.messages.create(
        model="claude-sonnet-4-6",
        max_tokens=1024,
        system="You are Aria, SkyLine Airlines support. Only discuss flights.",
        messages=conversation_history   # Full history sent every call
    )

    assistant_reply = response.content[0].text
    conversation_history.append({
        "role": "assistant",
        "content": assistant_reply
    })

    return assistant_reply
```

[click]

First, we keep conversation history client-side, in a plain Python list. Claude has no memory of previous turns — this list IS the memory.

[click]

Second, the function signature appends each incoming user message to history before we make any API call. That way Claude sees the user's NEW turn in context.

[click]

Third — the API call itself. We pass the same `system` value every time, alongside the FULL history. The system prompt sits in its own parameter — never inside the `messages` list.

[click]

Fourth, we capture Claude's reply, append it to history so the next turn has full context, and return it. Up next: what happens when we actually run this across three real turns.

## SLIDE 9: When to Use the System Parameter vs. User Messages

**Visual**: Two-column table on a white background. Column headers: "Use the `system` parameter" and "Use `messages` content." Rows list scenarios: system column shows persona/role definitions, output format constraints, safety guardrails, tool usage policies. User message column shows one-off instructions, user-specific context for that turn, dynamic data injected per request.

Not every instruction belongs in the system prompt. Here's the decision framework, side by side.

[click]

The left side — use `system` for anything that must be true for every turn. Persona and role definitions go here. Output format constraints — like "always respond in JSON" — go here. Safety guardrails and topic restrictions go here. Tool usage policies too. These are the standing rules of the conversation.

[click]

The right side — use the `messages` array for anything specific to a single turn. Dynamic data like a customer's account details. One-off instructions for the current question. Turn-specific context that doesn't apply to the rest of the conversation. The rule of thumb: if it needs to be true for every single exchange, it belongs in the system parameter. ## SLIDE 10: Exam Tip

**Visual**: Amber callout box. Title: "Exam Tip". Icon: target/bullseye. Text: "System prompts persist. First user messages don't."

Exam Tip time. The headline is simple — system prompts persist, first user messages don't. Two callouts make this concrete.

[click]

First, the distractor pattern. Putting persona or role instructions in the first user message and assuming they'll persist through the conversation. They won't, reliably. User messages are conversation history — they can be truncated, and their influence on later turns is not guaranteed.

[click]

Second, the exam signal. When you see a scenario where a bot "forgets" its persona or breaks its rules after several turns, the root cause is almost always instructions placed in a user message rather than the system parameter. Remember Scenario 1 is one of the heaviest Domain-4 hitters — skipping this trap isn't an option. Last up, the takeaways to lock in.

## SLIDE 11: Key Takeaways

**Visual**: Clean bullet list on light background. Title: "What to Remember".

Four things to hold onto from this lecture.

[click]

First — the system parameter is a top-level field outside the messages array. It sits alongside `model` and `max_tokens`, never inside the conversation list. If you only remember one thing from this lecture, remember that.

[click]

Second — system prompts persist across turns. You pass the same `system` value on every API call, and it's never confused with conversation history.

[click]

Third — user messages are not guaranteed to be persistent across turns. Instructions placed in the first user message are part of conversation history. They can be truncated when you trim history to save tokens, and they don't behave like true system-level constraints.

[click]

Fourth — the rule of thumb. Use `system` for persona, output format, safety rules — anything that must be true for the entire conversation. Use `messages` for turn-specific data and dynamic context.
